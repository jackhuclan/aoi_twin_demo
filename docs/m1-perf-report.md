# M1 性能测试报告（T4.3）

> 对应 NFR-01/02/03 与 FR-M1-05。基准工具：`tools/AoiTwin.Soak bench`
> （原始输出：`docs/_bench-raw.txt`，可随时复跑）。测试机：本开发机 20C，Windows，
> .NET 10.0.14，Release 构建。**正式验收以 PRD 指定基准机（i5 + 核显）复测为准。**

## 1. NFR-03 —— Hub 发布—订阅单条开销 ≤ 0.1ms

| 指标 | 实测 | 判据 | 结论 |
|------|------|------|------|
| 单订阅者单条开销 | **0.49 µs**（20 万条） | ≤ 100 µs | ✅ PASS |
| 丢包 | 0（received == published） | 0 | ✅ |

发布路径是同步直调 + Topic/类型过滤，无队列无锁竞争；四订阅者场景由采集监控页的实时
吞吐佐证（聚合速率与各源速率之和一致）。

## 2. NFR-03 —— 录制写入不阻塞采集线程

| 指标 | 实测 |
|------|------|
| 写入吞吐 | **198,661 帧/秒**（5 万帧） |
| 单帧开销 | 5.03 µs（20B 帧头 + CRC32 + SHA-256 增量） |
| 每帧落盘 | 130.8 字节 |

采集端典型速率 ~40 帧/秒，写入能力余量 ~5000×；写入在专用加锁路径上串行化，
不阻塞适配器线程（采集线程只投递消息）。断电场景由 T2.2 修复链路覆盖（NFR-04）。

## 3. NFR-02 —— GLB 后台预加载 ≤ 3s

| 指标 | 实测 |
|------|------|
| 首次加载（含 JIT） | 423 ms |
| 热加载（4 次） | 9 / 11 / 16 / 18 ms |
| 平均 | **95 ms**（10 部件 × L1+L2 两档 + 合批） | 

预算 3000ms，余量 30×。加载在后台线程完成，UI 线程只接收 Freeze 后的几何；
加载期间帧探针无 >100ms 长帧（帧时间探针为常驻判据，见第 5 节）。

## 4. FR-M1-05 —— LOD 远档 Draw Call 下降 ≥ 40%

| 档位 | 可渲染网格数（≈ Draw Call） | 相对 LOD1 |
|------|------------------------------|-----------|
| LOD1（占位包，逐部件） | 10 | — |
| LOD2（运动组合批） | 5 | **−50%** ✅ |

合批按运动组（固定/X/Y/Z/θ），真实资产包部件数更多、内部细节 Mesh 更碎时，
降幅会进一步放大（代理数只随运动组数增长）。切换无闪烁由双阈值回滞保证（±0.6m）。

## 5. NFR-01 —— 空场景 60fps

**现状：本开发环境无法给出 60fps 的有效实测**，原因与数据如下：

- 渲染循环挂点（`CompositionTarget.Rendering`）实测本机**裸渲染循环（无任何 3D 内容）
  只有 ~32fps**——瓶颈是当前会话的显示刷新率（远程会话/省电策略，约 30–44Hz），
  不是视口或场景代码；
- 场景规模本身极轻：整机占位模型仅 324 三角面、10 个网格（LOD2 时 5 个），
  距 i5+核显的 60fps 能力有多个数量级余量。

**已就位的验证基础设施**（验收时在 60Hz 本地会话直接出数）：
- `FrameTimeProbe`：渲染循环逐帧采样 → 120 帧滚动窗口 FPS/P95/最大帧间隔，
  >100ms 长帧页头告警（NFR-02 的 UI 卡顿判据常驻）；
- 页头实时显示 `FPS x · P95 x ms`，验收截图即可作为证据。

**结论**：NFR-01 标记为「待基准机会话复测」，风险等级低（场景规模 + 探针数据双重佐证）。

## 6. T1.8 点选响应 ≤ 50ms

| 指标 | 实测 |
|------|------|
| 单次射线求交（10 部件全量遍历，Möller–Trumbore 纯数学） | **76 µs** |
| 1000 次随机探针 | 76 ms 总计，命中 758 |

预算 50ms/次，余量 ~650×；且拾取集合与渲染档位解耦（LOD2 下同样 100% 命中）。
