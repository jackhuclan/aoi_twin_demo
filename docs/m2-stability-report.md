## 1. 判据（计划原文 → 可执行量）

| # | 判据 | 报告中字段 | 通过条件 | 备注 |
|---|---|---|---|---|
| 1 | 无崩溃 | `result` / `<report>.progress` 尾行 | 跑满计划时长且 `result=PASS` | 进程被杀时报告写不出，心跳文件停在哪一分钟即死亡时间 |
| 2 | 内存增长 < 100MB | `maxGrowthMB` | 预热后工作集增量 < 100 | 基线取预热结束后的首个采样点，剔除 JIT/GLB/GPU 表面的一次性开销 |
| 3 | 帧率衰减 < 5% | `fpsDecayPercent` | `(基线 − 末段) / 基线 < 5` | 基线取预热后前 5 分钟均值，末段取最后 3 个采样点；`frameClock=stalled` 时跳过 |
| 附 | 无降态 | `handlerErrors` | = 0 | 消息处理异常被捕获后不中断渲染，但**算稳定性失败** |
| 附 | 无挤压 | `droppedWafers` | = 0 | 上传队列容量 8，渲染线程跟得上就不该丢片 |

第 1 条是二值事实，第 2/3 条是趋势判据——所以报告除了给结论，还给了 `growthRateMBPerHour`
与 `.csv` 曲线：100MB 是门槛，增长速率才是判断「有界还是线性」的证据。

## 2. 执行方式

```bash
# 现场（72h，窗口 B）：一键脚本，默认 4320 分钟、采样 30s、预热 30min
tools\soak-visual.cmd

# 等价直调（可指定资产根/节拍/窗口尺寸）
AoiTwin.Soak soak-visual 4320 D:\soak\winB.txt --sample-sec 30 --warmup-min 30

# 离线冒烟（1 分钟，确认工具本身可用）
AoiTwin.Soak soak-visual 1 docs\_soak-visual-smoke.txt --sample-sec 10 --warmup-min 0.1
```

| 参数 | 缺省 | 说明 |
|---|---|---|
| `<minutes>` | 必填 | 计划时长（分钟，可小数） |
| `<reportPath>` | 必填 | 报告路径；同目录生成 `.progress`（心跳）与 `.csv`（曲线） |
| `--assets <dir>` | 向上查找 | 资产根；缺省从可执行目录向上找 `assets/part-catalog.json` |
| `--wafer-sec <6.5>` | 6.5 | 晶圆结果间隔（PRD 节拍）。**改小等于放大缺陷点云增长，判据会失真** |
| `--defects <4>` | 4 | 每片缺陷数均值（Mock 场景参数） |
| `--size <1600x900>` | 1600x900 | 渲染窗口尺寸 |
| `--visible` | 关 | 窗口可见（默认移到屏幕外，不挡班次界面） |
| `--sample-sec <30>` | 30 | 采样周期 |
| `--warmup-min <5>` | 5 | 预热时长（超过计划时长 10% 时按 10% 收） |

退出码：`0` 判据全过 ｜ `1` 判据未过 ｜ `2` 参数错误 ｜ `3` 环境/资产不可用（含无桌面会话）。

### 输出三件套

| 文件 | 内容 | 用途 |
|---|---|---|
| `<report>` | 键值报告：环境、场景、判据、抽稀后 ≤240 行采样明细 | 评审签字、归档 |
| `<report>.progress` | 每个采样点一行，逐行 flush | **崩溃物证**：跑挂时看最后一行时间戳 |
| `<report>.csv` | `elapsedSec, workingSetMb, privateMb, managedHeapMb, fps, p95FrameMs, wafers, defectPoints, ...` | 画内存/帧率曲线，定位拐点 |

## 3. 观测设计（为什么这么测）

长跑工具最容易被做成「跑一夜、看没崩、签个字」。下面五条是刻意的取舍，现场解释得清：

**① 必须开窗，不能用计时器假装帧循环。**
WPF 的帧节拍来自窗口合成（`CompositionTarget.Rendering`）。没有窗口就只有计时器空转，
量出来的是「我能多快调用驱动器」，不是「渲染一帧要多久」。所以工具一定建窗口并真挂视口。

**② 窗口默认移到屏幕外，但不隐藏。**
`Left/Top = −20000`：仍在合成、仍在渲染，但不占操作员的班次界面。
用 `Visibility.Hidden` 或最小化会**停掉渲染**，那是自欺欺人。

**③ 合成中断要能看见，而不是悄悄变成零帧。**
远程桌面断开、窗口被最小化、显卡驱动重置，都会让 `CompositionTarget` 停摆。
此时 1s 看门狗在「连续 2s 无帧」后兜底泵一帧（保证 VM 与六路驱动器仍被驱动），报告标 `frameClock=stalled`，
并 **`fpsDecayOk=SKIPPED`**——空转帧数不能拿来当帧率。现场看到 `stalled` 的正确动作是：
接回控制台/桌面重新跑，而不是引用这份报告的帧率。

**④ 数据源用 Mock 四路适配器，节拍按现场取。**
与采集页、数据集生成器同一份装配（`MockCollectionFactory`），链路不是测试专用简化。
晶圆间隔按 PRD 节拍 6.5s：每片 4 个缺陷，72h ≈ 4.0 万片 / 16 万点。
把这个值调到 0.5s，缺陷点云会变成 52 万片 / 200 万点，内存曲线必然线性上扬——
那不是泄漏，是把 72h 压成了 720h 的工作量。

**⑤ 挂满现场实际挂的层。**
六路同步驱动器（运动/光学/视野锥/WaferMap/缺陷点云/装载）+ 报警脉冲 + 传输粒子 + 跟随相机，
装配顺序与 `TwinView.xaml.cs` 一致。粒子与报警壳每帧都在改可视树，是典型的泄漏源，
只测同步层等于漏测一半。

## 4. 离线实测（本机，30 分钟全链路）

> 环境：`SU104003344` · 20C · Windows NT 10.0.26300 · .NET 10.0.14 · Release 构建
> 场景：真实 GLB（16 部件 / 468 三角面 / LOD1 16 网格 / LOD2 7 网格）· 窗口 1600×900 屏幕外
> 数据：Mock 四路，wafer 6.5s、每片 4 缺陷 · 采样 30s · 预热 3min

<!-- MEASURED:START -->
| 判据 | 实测 | 判定 |
|---|---|---|
| 无崩溃 | 跑满 30:00 自行退出，`result=PASS`，退出码 0 | ✅ |
| 内存增长 < 100MB | 基线 420MB → 峰值 429MB，`maxGrowthMB=9`；**21 分钟后锁定 428MB，末 10 分钟 20 个采样点零增长** | ✅ |
| 帧率衰减 < 5% | 基线 58.0 → 末段 58.1fps，`fpsDecayPercent=-0.08`（无衰减） | ✅ |
| 附：无降态 | `handlerErrors=0` | ✅ |
| 附：无挤压 | `droppedWafers=0`（278 片全消费） | ✅ |

渲染侧明细：`framesRendered=104 339`、`framesPumped=0`（**全部是真实合成帧，无看门狗兜底**）、
`longFrames=3`（>100ms 占 0.003%，均为首屏与 GC 瞬时）、P95 帧时 18.8–19.8ms、
`gc.gen2=1`、点云 1123 点（30 分钟 278 片 × 4 缺陷）。

原始产物：`docs/_soak-visual-30m.txt`（报告）、`docs/_soak-visual-30m.txt.csv`（60 点曲线）。

**怎么读这组数**：

- 工作集在 20 分钟左右完成爬升后**完全持平**（`428MB` 连续 20 个采样点不变），
  这是「有界」的形态；若是泄漏，曲线会在同一斜率上继续走。
- 58fps 而非 60：屏幕外窗口 + 本机 20 核共享核显（Iris Xe），单帧 P95 19.5ms 说明
  偶发合成排队。判据看**衰减**不看绝对值，绝对值留给窗口 B 的目标机复核。
- `growthRateMBPerHour=NA`：时长不足 1h 时工具不换算速率，避免把 9MB/0.5h 说成 18MB/h
  这种看着吓人却无统计意义的数字。
<!-- MEASURED:END -->

**说明**：30 分钟只够证明「工具与判据可用、曲线进入平台」，**不能替代 72h 结论**——
线性泄漏在 30 分钟内通常看不出来。本节的定位是「执行前的自检证据」，
72h 结论以窗口 B 的报告为准，届时在同名段落追加。

## 5. 现场作业流程（窗口 B，72h）

### 班前（15 分钟）

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 桌面会话 | 本机有可用桌面（远程桌面也可，但跑完需确认 `frameClock=rendering`） |
| 2 | 资产包 | `assets/part-catalog.json` 与 GLB 为评审冻结版本；报告 `scene=glb` |
| 3 | 标定文件 | `assets/teach-calibration.json` 为窗口 A 入库版本（报告 `scene` 段无 `fallbackReason`） |
| 4 | 磁盘 | 报告目录可用空间 ≥ 2GB（`.progress` 72h ≈ 2 万行、`.csv` 同量级） |
| 5 | 电源/睡眠 | 关闭睡眠与自动更新重启（`powercfg /change standby-timeout-ac 0`） |
| 6 | 版本 | 与 CI 同版本号的 Release 构建（报告 `version` 段可比对） |

### 启动

```bat
tools\soak-visual.cmd 4320 D:\soak\winB-<设备号>-<日期>.txt
```

启动后确认三件事：控制台出现第一行 `sample t=00:00:29 ...`；`.progress` 文件在增长；
任务管理器里能看到一个屏幕外的窗口进程（`AoiTwin.Soak.exe`，工作集约 400–500MB 起）。

### 巡检（每班次一次，2 分钟）

| 看什么 | 正常 | 异常处置 |
|---|---|---|
| `.progress` 尾行时间 | 距现在 < 1 分钟 | 停更 = 卡死，看尾行时间定位，保留文件重跑 |
| `fps` | 与基线差 < 5% | 单点抖动忽略；连续 3 点下滑记录时间点 |
| `ws` | 平台或缓慢上升 | 单调快速上升 → 记拐点时间，收口后查 `points`/`heap` 归因 |
| `errors` | 0 | > 0 即降态，收口后查 `HandlerError` 主题 |
| `drops` | 0 | > 0 说明渲染线程被拖住，同时看 `p95` |

### 收口

跑满时长后进程自行退出并落报告。核对 `result`，然后把
`<report>`、`<report>.csv`、`<report>.progress` 三者一起归档到
`docs/field/2026-xx-winB/`（**不进 git**，只登记路径与结论），并在 §6 签字表登记。

## 6. 判读规则（怎么从报告读出结论）

| 现象 | 结论 | 归因方向 |
|---|---|---|
| `result=PASS` | 三条判据全过 | — |
| `memoryGrowthOk=False` 且 `points` 同步线性增长 | 缺陷点云无保留策略 | `DefectPointDriver` 按 DefectId 累加、无淘汰（见 §7-1），属**设计缺口**，不是泄漏 |
| `memoryGrowthOk=False` 且 `heap` 上升、`points` 平 | 托管侧持有 | 看 `gen2` 次数与 `p95`，优先怀疑每片新建纹理/几何未释放 |
| `memoryGrowthOk=False` 且 `private` 涨、`heap` 平 | 非托管/GPU 侧 | WPF 渲染目标或位图未释放；对比 `framesRendered` 与 `p95` |
| `fpsDecayOk=False` 且 `p95` 上升、`ws` 平 | 帧预算变紧 | 检查点云点数与叠加层可视树规模（线性扫描类退化） |
| `fpsDecayOk=SKIPPED` | 渲染停摆 | 见 §3-③，重跑，不要引用 |
| `handlerErrors>0` | 降态 | 按异常 Topic 定位；M2 的 `Guarded<T>` 已保证不中断渲染 |
| `scene=synthetic` | 跑的不是真资产 | 资产包缺失/损坏，结论不可用于验收 |

## 7. 已知风险与待决

| # | 项 | 影响 | 处置 |
|---|---|---|---|
| 1 | **缺陷点云无保留策略**：`DefectPointDriver` 按 `DefectId` 永久累加，无按班次/按片淘汰 | 72h 现场片数越多内存越高，100MB 判据可能被「工作量」而非「泄漏」顶破 | 长跑报告已单列 `defectPoints` 供归因；保留策略（按班次清空 / 保留最近 N 片）需产品确认，建议随 M3 持久化 Sink 一并定 |
| 2 | 核显档位未覆盖 | NFR-11 要求真机 + 核显两档 | 窗口 B 至少安排一台核显机跑 8h 版本，`baselineFps` 会显著低于独显档，判据仍看**衰减**不看绝对值 |
| 3 | 远程桌面下 `frameClock=stalled` | 帧率判据失效 | 报告已标 `SKIPPED`；现场以 `.progress` 的 fps 字段判断是否可信 |
| 4 | 窗口尺寸固定 1600×900 | 与实际工位分辨率可能不同 | 用 `--size` 对齐工位分辨率后重跑；像素填充率直接影响帧率 |
| 5 | 未包含 LOD 自动换档 | 换档是整树重建，属已知抖动源（M1 已测） | 长跑不换档；换档抖动由 `TwinView` 冒烟覆盖，M3 若有长时巡检再加 |
